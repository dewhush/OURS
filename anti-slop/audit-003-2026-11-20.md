## 1. Authentication / Token security

### S1 — `server/src/auth.rs:219-251` — AuthUser extractor runs token verification AND DB revocation check, but the revocation check race is tight
`from_request_parts` reads `claims.iat_ms` then checks `revoked_before` in a `spawn_blocking` block. The window between `verify_access_claims` (which only checks expiry) and the DB revocation check is ~0 because both are in the same borrow, **but** `verify_access_claims` does not itself check revocation — an access token minted before a logout (`tokens_revoked_before`) but whose expiry is still in the future will pass `verify_access_claims` and only be caught at the DB step. That is correct as-is (the DB check exists), **however** the edge case is: a token minted at `t0`, user logs out at `t1` setting `tokens_revoked_before = t1`, token's `iat_ms = t0 <= t1` → rejected. This is **fine**. No fix needed. Confirmed correct.

**Verdict**: PASS. The revocation timing is correct; `iat_ms <= revoked_before` is the right comparison.

### S1 — `server/src/auth.rs:78-85` — Access token expiry check uses `payload.exp <= now` (leaky)
Edge case: a token whose `exp == now` is rejected. This is correct behavior (expiry at current ms means it's already expired). No fix.

**Verdict**: PASS.

### S2 — `server/src/auth.rs:100-108` — `hash_device_id` returns `None` for device IDs shorter than 8 chars
A client can supply a 7-char device ID, get `None` as the stored hash (via `req_device_hash.as_deref()` → `None`), and bypass device-bound login. In `finish_google_auth` (pair.rs:1075-1079), `device_ok` is `stored_device_hash.as_deref().is_some_and(...)` — when `req_dev_hash` is `None` (because `hash_device_id` returned `None`), `device_ok = false`. That is **correct**: a missing/short device ID never satisfies device binding. The attack surface is: an attacker who knows a victim's email but not their device ID cannot login because `device_ok = false`, and the remaining gates (verified token / setup key / invite) still hold. No bypass.

**Verdict**: PASS — the `None` path correctly fails device_ok. But note: a 7-char device ID is silently degraded, not rejected. Consider returning an error from the client side. Low concern.

### S2 — `server/src/auth.rs:92-96` — `hash_refresh_token` uses plain SHA-256 with no salt
An attacker with DB access (e.g., SQL injection — see S4 below) gets `refresh_token_hash` values that are raw SHA-256 of the base64 refresh token. A rainbow table for common base64 tokens is feasible. The refresh token is 32 random bytes base64-encoded (~43 chars of high entropy), so preimage attack is infeasible in practice. But for defense-in-depth, add a static per-deployment salt (from `token_secret`) so a DB leak doesn't give the attacker trivially comparable hashes.

**Fix**: `hash_refresh_token` should HMAC with `token_secret`:
```rust
// auth.rs:92
pub fn hash_refresh_token(token: &str, secret: &[u8]) -> String {
    let mut mac = HmacSha256::new_from_slice(secret).unwrap();
    mac.update(token.as_bytes());
    hex::encode(mac.finalize().into_bytes())
}
```
And update all callers (`pair.rs:295`, `pair.rs:375`, `pair.rs:389`) to pass `&state.config.token_secret`. Currently the function is called without the secret, which is the core issue.

**Verdict**: S2 — low real-world risk given 32-byte random tokens, but a DB leak makes these hashes trivially comparable across installations that share the same (lack of) salt. Fix is cheap.

### S3 — `server/src/auth.rs:88-90` — `verify_access_token` is a thin wrapper, unused in favor of `verify_access_claims`
`verify_access_token` exists but the `AuthUser` extractor (line 214) calls `verify_access_claims` directly. Dead code, not a bug. Cosmetic.

**Verdict**: S4 — remove or use.

### S3 — `server/src/auth.rs:235-239` — last_seen_at update has a 60s staleness threshold but is inside the auth extractor
Every authenticated request updates `last_seen_at` if the user hasn't been seen in 60s. This is fine and intended (used by the wake check in jobs.rs). No issue.

**Verdict**: PASS.

## 2. Rate limiting

### S2 — `server/src/state.rs:22-49` — `SlidingLimiter` is an in-memory `Mutex<HashMap<String, Vec<Instant>>>`
Rate limit state is per-process. In a multi-instance deployment (e.g., behind Cloudflare with 2+ server instances), each instance has its own limiter, so an attacker can spread attempts across instances and bypass the per-instance cap. The `client_rate_key` in pair.rs uses `CF-Connecting-IP` which is a Cloudflare edge header, so the IP identity is consistent — but the **counters** are per-instance. With N instances, the effective limit is N× the configured cap.

For a 2-person app this is low-risk in practice (the app is not a public API), but the audit should flag it: if the server ever runs behind a load balancer with >1 backend, the rate limits are N× weaker than configured.

**Fix**: For now, document the single-instance assumption. If multi-instance is ever needed, move the limiter to Redis or a shared SQLite table. The current `SlidingLimiter` struct is not shared across connections.

**Verdict**: S3 — acceptable for a 2-user LAN/tunnel app, but not future-proof. Document the constraint.

### S3 — `server/src/state.rs:105-112` — `check_user_action` / `record_user_action` for nudge, SOS, messages, checkins, places
Nudge is limited to 1 per 30s (events.rs:25-26), SOS to 3 per 5min (events.rs:27-28), messages to 60/min (messages.rs:22), checkins to 50/day (checkins.rs:24), places to 50/day (places.rs:16), replies to 30/min (checkins.rs:25), highlights to 30/min (checkins.rs:26). All reasonable. No missing rate limits detected.

**Verdict**: PASS.

### S3 — `server/src/state.rs:189-244` — `get_google_jwk` and friends fetch JWKS over HTTP with no timeout on the JSON body parse
The `http_client` has a 6s timeout (state.rs:82-84). JWKS endpoints are Google-operated and fast. The `.json().await` call could in theory hang if the server returns a slow streaming response within the 6s window. In practice, Google's JWKS is fast and small. Low risk.

**Verdict**: S4 — acceptable. The 6s timeout covers the full fetch.

### S3 — `server/src/pair.rs:937-964` — Google auth rate limit: 12/min per IP pre-check, plus per-email scoping
The `google_auth_pre` key limits garbage-token floods. On failure, `record_google_auth_failure` is called against the IP key AND the scoped email key AND the email-rate-key (pair.rs:1009-1011, 1166-1169). This is well-scoped. No fix.

**Verdict**: PASS — the multi-key scoping (IP + email + email-scoped) is correct and prevents both IP rotation and email enumeration attacks.

### S3 — `server/src/pair.rs:52-81` — `client_rate_key` trusts `CF-Connecting-IP` only when peer is loopback
The function only trusts `CF-Connecting-IP` when the TCP peer IP is loopback (local reverse proxy) or absent (test). A direct non-loopback client cannot spoof the rate-limit key via headers. This is correct DP. The test at integration.rs:1933-1963 verifies this.

**Verdict**: PASS.

## 6. JWT / Token security

### S2 — `server/src/auth.rs:39-56` — `sign_access_token` uses HMAC-SHA256 with a custom JWT-like format (base64 payload . base64 signature)
The token format is: `base64url(payload_json).base64url(hmac_sha256(payload_b64))`. This is a custom format, not RFC 7519 JWT. The payload contains `uid`, `exp`, `iat_ms`. HMAC-SHA256 is a sound choice for symmetric token signing. The `iat_ms` is included and used for revocation checking (auth.rs:232).

**Potential issue**: The token does not include a `jti` (JWT ID) or any unique identifier. This means you cannot revoke a single token — you can only revoke all tokens issued before a timestamp (`tokens_revoked_before`). The refresh-token family mechanism handles refresh token revocation, but access tokens are stateless and can only be revoked globally per-user via `tokens_revoked_before`. For a 2-user app with 1-hour access tokens, this is acceptable. But note: logout (pair.rs:368-408) sets `tokens_revoked_before = now`, which revokes ALL access tokens for that user, including any other devices. This is documented behavior.

**Verdict**: PASS for the app's threat model. The global revocation on logout is the design.

1 hour is reasonable. No fix.

**Verdict**: PASS.

### S3 — `server/src/auth.rs:22-23` — Refresh token TTL = 180 days

**Verdict**: PASS.

### S3 — `server/src/auth.rs:137-146` — `issue_tokens` deletes expired refresh tokens before inserting

**Verdict**: PASS.

### S3 — `server/src/auth.rs:58-86` — `verify_access_claims` rejects tokens without a valid HMAC signature
The signature is verified before the payload is decoded. Correct order. No fix.

**Verdict**: PASS.

### S3 — `server/src/pair.rs:719-789` — `verify_jwt_with_rsa_components` validates iss, aud, email_verified
The function sets `validation.set_issuer` and `validation.set_audience` based on the provider. For legacy Google, it validates `iss=https://accounts.google.com` and `aud=google_client_id`. For Firebase, `iss=https://securetoken.google.com/<proj>` and `aud=proj`. For OIDC, `iss=OURS_OIDC_ISSUER` and `aud=one of OIDC_CLIENT_IDS`. This is correct.

**One concern**: at pair.rs:742-743, when `auds` is empty, `validation.validate_aud = false`. The OIDC path at pair.rs:844 ensures `audience` is non-empty before calling (the `if !audience.is_empty()` check at pair.rs:844). Legacy Google at pair.rs:875 always sets `aud_refs`. Firebase at pair.rs:806 always sets `aud_refs`. So the `validate_aud = false` branch is only hit when the caller passes an empty audience slice, which doesn't happen in the current code paths. Correct.

**Verdict**: PASS.

### S3 — `server/src/pair.rs:791-831` — `verify_id_token` tries Firebase first, then falls through to OIDC / legacy Google
The function routes by **signature** (kid lookup in each provider's JWKS), not by the token's `iss` claim. This is the correct "let the signature decide" approach described in the code comment. No issuer-pinning bypass.

**Verdict**: PASS — the routing is signature-first, not claim-first.
