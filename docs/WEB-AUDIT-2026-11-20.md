## 1. DESIGN TOKEN CONSISTENCY

### 1.1 — Inconsistent avatar border tokens (app.js:2964)
**File:** `web/app.js:2964`
**Issue:** The chat header avatar uses `border: 2px solid var(--pin-ring)` but `map-pin-dot` (styles.css:1659) uses `border: 2.5px solid var(--pin-ring)`. The avatar–map pin visual mismatch is visible at the same zoom.
**Fix:** Use `2.5px` on the chat avatar to match `map-pin-dot`, or introduce `--pin-ring-width: 2.5px` and reference it in both places.

### 1.2 — Unused dark-only token `--glass-card-rim` (styles.css:257-258)
**File:** `web/styles.css:257-258`
**Issue:** `--glass-card-rim` and `--glass-card-rim-w` are defined only in `:root[data-theme="dark"]` (line 257-258) and only consumed by `.card::before` (styles.css:947). Light mode cards get no gradient rim because the variable is missing from the light `:root`.
**Fix:** Move `--glass-card-rim` and `--glass-card-rim-w` into the base `:root` (light) block, or accept that light cards intentionally have no rim (remove the `::before` rule's dependency). Current behavior: light cards render a rim using an undefined variable → no rim painted.

### 1.3 — Hardcoded color values in map-pin CSS instead of tokens (styles.css:1600, 1622, 1623)
**File:** `web/styles.css:1600, 1622-1623`
**Issue:** `.map-checkin-pin` background is hardcoded `#FFFFFC` (line 1600), `::after` background is hardcoded `#FFFFFC` (line 1622), pin shadow uses hardcoded rgba. These should use `--bg-surface` / `--surface` tokens so they respond to dark mode.
**Fix:** Replace `#FFFFFC` with `var(--surface)`; the pin currently looks identical in dark mode because the token value is `#FFFFFC` in dark too, but if the light token ever changes, the pin breaks.

### 1.4 — Orb blur radius inconsistent across themes (styles.css:353)
**File:** `web/styles.css:353`
**Issue:** `.ambient-orb` uses `filter: blur(44px)` hardcoded. The dark theme orbs use different color stops but the same 44px blur. No `--orb-blur` token exists.
**Fix:** Introduce `--orb-blur: 44px` and reference it, so the value can be tuned per tier.

### 1.5 — Map style JSON colors don't reference the CSS token palette (map-style-light.json, map-style-dark.json)
**File:** `web/assets/map-style-light.json`, `web/assets/map-style-dark.json`
**Issue:** The JSON map styles use hardcoded hex values that approximately match the CSS tokens but are not derived from them. E.g. light `background-color: #F4F3EE` vs CSS `--map-canvas-bg: #F4F3EE` (match), but `landuse_residential: #E9E7DF` has no CSS equivalent; the CSS `--bg-surface-muted` is `#F0EFE9`. Dark mode `landuse_residential: #121723` vs CSS `--bg-surface: #131722` — off by one shade.
**Fix:** Document the decision that map styles are independently tuned (acceptable, since MapLibre styles aren't themed by CSS). Add a comment in both JSON files listing the canonical CSS hex they target: `--map-canvas-bg`, `--bg-surface`, `--bg-surface-muted`, `--ink-secondary`, `--ink-muted`.

## 2. CSS SPECIFICITY ISSUES

### 2.1 — Duplicate `background` declaration on `.card` (styles.css:921-922)
**File:** `web/styles.css:920-929`
**Issue:**
```css
.card {
  background: var(--glass-card, var(--glass-strong));
  background: var(--glass-strong);
  ...
}
```
Line 921 sets a fallback; line 922 immediately overrides it with no fallback. The cascade means line 922 always wins — line 921 is dead.
**Fix:** Remove line 921, or if the fallback was intentional for when `--glass-strong` is missing, merge into one declaration with the fallback.

### 2.2 — `.card::before` rim only paints in dark mode (styles.css:940-953)
**File:** `web/styles.css:940-953`
**Issue:** The `::before` gradient rim uses `var(--glass-card-rim)` which is only defined in `[data-theme="dark"]`. Light mode cards silently get no rim. Combined with 1.2.
**Fix:** See 1.2. If light rim is intentional, define the variable in the base `:root`.

### 2.3 — High-specificity inline style overrides in JS template literals (app.js:1802, 1898, 1902, 2469, etc.)
**File:** `web/app.js` — multiple
**Issue:** Many template literals inject `style="..."` attributes with hardcoded values that override CSS classes:
- `app.innerHTML` onboarding: `style="background:transparent"` (line 1802, 1878)
- `h1` font sizes in template: `style="margin:0;font-size:26px..."` (line 1829), `style="margin:0 0 2px;font-size:28px..."` (line 1898)
- Card in onboarding: `style="display:flex;flex-direction:column;gap:14px;border-radius:26px;padding:18px"` (line 1902)
- Map overlay HTML: many inline `style` attributes on divs (lines 2083-2341)

These aren't "bugs" but they bypass the token system. If a designer changes `--text-heading` size, the onboarding `h1` at `28px` won't follow.
**Fix:** Extract recurring inline styles to classes: `.onb-title` (28px/800/-0.03em), `.onb-subtitle` (row-sub), `.onb-card` (rounded card with gap). Replace inline `style` attributes with class names in the template literals.

### 2.4 — `.segmented` base + `.settings-theme-seg` override conflict (styles.css:1056-1063 vs 1106-1112)
**File:** `web/styles.css:1056` and `1106`
**Issue:** `.settings-theme-seg` redefines `display:flex; align-items:center; width:198px; height:34px; padding:3px; border-radius:17px` which overlaps with `.segmented` base. If the settings theme segmented control is used elsewhere, it inherits 198×34 vs the 32px default. Not a bug today but fragile.
**Fix:** Derive `.settings-theme-seg` from `.segmented` using modifier-only overrides: `.segmented.settings-theme-seg { width:198px; height:34px; border-radius:17px; }`.

### 2.5 — `.nav-item svg` width/height in styles.css (styles.css:696-698) vs `svgIcon()` width in app.js (app.js:1492-1509)
**File:** `web/styles.css:696-698`, `web/app.js:1492-1509`
**Issue:** `.nav-item svg` sets `width:15px; height:15px` (styles.css:697) but `svgIcon()` returns SVGs with hardcoded widths like `width="19"` (map, memories, chat, settings), `width="17"` (bell, home, briefcase, shield), `width="18"` (route, search, pin). In the bottom nav the CSS wins (15px), squishing the 19px icons. In the desktop rail, `svgIcon()` SVGs are placed without `.nav-item` wrapper so they render at their native 19px.
**Fix:** Either normalize all `svgIcon()` output to 15×15 for nav use, or add a separate `svgIconNav()` that returns 15×15 variants. Currently the nav looks consistent because CSS overrides — acceptable, but document the intentional override.

## 4. ACCESSIBILITY

### 4.1 — `aria-hidden="true"` on ambient orbs is correct (app.js:1797-1800, 1873-1876, 2441). ✅

### 4.2 — `sr-only` labels on inputs: used in onboarding (app.js:1931, 1935, 1939, 1942), memories search (app.js:2806), chat search (app.js:2982), places name/radius (app.js:3035-3037), settings server URL (app.js:3162), language/theme segmented buttons have **no** `aria-label` (app.js:3119-3120, 3111-3113).
**File:** `web/app.js:3109-3122`
**Issue:** Theme segmented buttons (`data-theme-set="system|light|dark"`) and language segmented buttons (`data-lang-set="en|id"`) have no `aria-label`. Screen readers announce them as "System", "Light", "Dark" (the button text) which is fine for theme, but the language buttons just say "EN" / "ID" with no context.
**Fix:** Add `aria-label="Theme"` to the segmented wrapper or `aria-label="Language"` on the language segmented container. Add individual `aria-label="English"` / `aria-label="Bahasa Indonesia"` on the language buttons.

### 4.3 — Switch components: `role="switch"` + `aria-checked` present (app.js:3128, 3148, 3486, 3493, 3500, 3507). ✅ But the privacy bubble sheet switches (app.js:3222-3223) are buttons with no `role="switch"` or `aria-pressed`.
**File:** `web/app.js:3222-3223`
**Issue:** The bubble on/off segmented buttons have state (active-blue class) but no ARIA state. A screen reader sees two unlabeled buttons.
**Fix:** Add `role="segmented"` (or `role="tablist"` with `role="tab"`) + `aria-selected` to the segmented buttons in the bubble sheet, or convert to `role="switch"` + `aria-checked` like the settings switches.

### 4.4 — Hold SOS pill: `aria-label` present (app.js:2299, 2302, 3290). ✅ But the `hold-fill` progress bar div has no `aria-label` or `role="progressbar"`.
**File:** `web/app.js:2091, 2292, 2300, 3291`
**Issue:** The `.hold-fill` div is a visual progress indicator for the 2-second hold. No ARIA role. A screen reader user gets no feedback during the hold.
**Fix:** Add `role="progressbar" aria-valuemin="0" aria-valuemax="2" aria-label="Hold 2 seconds for SOS"` to the fill element, and update `aria-valuenow` during the hold interval (in `wireHoldSosButton` / `startHold`).

### 4.5 — `hydratePhotos()` sets `img.onload` after `img.src` assignment (app.js:1420-1422)
**File:** `web/app.js:1419-1422`
**Issue:**
```js
img.onload = () => img.classList.add("photo-loaded");
img.src = objUrl;
if (img.complete) img.classList.add("photo-loaded");
```
If the image loads synchronously (from cache), `onload` may not fire, but `img.complete` catches it. However, `onload` is assigned *before* `src`, so it's correct for async loads. This is OK. ✅ But: if `img.complete` is true because the image failed to load (e.g. 404 blob), `photo-loaded` is added incorrectly.
**Fix:** Check `img.naturalWidth > 0` in addition to `img.complete` before adding `photo-loaded`.

### 4.6 — Color contrast: Electric Blue `#0055FF` on white `#FFFFFC` = 4.48:1 (passes AA for large text but borderline for normal text at 4.5:1). On `var(--action-soft)` `#EBF1FF` background, `#0055FF` text = ~2.3:1 — **fails AA**.
**File:** `web/components.css:605` (`.ours-bubble--me` uses `var(--glass-electric)` background), `app.js:2857` (bubble me uses `var(--glass-electric)`).
**Issue:** `.ours-bubble--me` background is `var(--glass-electric)` (a light blue gradient). The bubble text is `var(--ink)` (near-black) — OK on the gradient. But the time label uses `var(--ink-muted)` on the same gradient — potentially low contrast.
**Fix:** Verify the actual rendered contrast with a tool. The gradient is mostly white-ish, so `#555B68` (ink-muted) on white = 5.5:1 — OK. Not a real failure, but document that `--ink-muted` on `--glass-electric` should be checked.

### 4.7 — Focus management: modals call `firstFocusable.focus()` (styles.css... actually app.js:3200-3201). ✅ Escape closes modals (app.js:4474-4476). ✅ But: `openModal` sets `root.onclick` to close on backdrop click (app.js:3191-3193) — good. But the `modal-root` has no `aria-hidden` toggle on the main app behind it.
**File:** `web/app.js:3182-3210`
**Issue:** When a modal opens, the underlying app content remains in the DOM and is not hidden from screen readers. No `aria-hidden` on the app shell, no focus trap.
**Fix:** Add `aria-hidden="true"` to `#app` when a modal is open (and remove on close). Implement a basic focus trap: on `keydown Tab`, cycle within the modal. For a minimal app this is acceptable, but document it.

### 4.8 — `nav-unread-dot` (styles.css:701-709) has no `aria-hidden` or `aria-label`.
**File:** `web/styles.css:701-709`
**Issue:** The dot is a visual indicator on the chat nav item. It has no `aria-hidden="true"`, so a screen reader might announce an empty element.
**Fix:** Add `aria-hidden="true"` to `.nav-unread-dot` (it's decorative — the unread count is already conveyed by the badge text or the unreadAlerts state).

## 5. RESPONSIVE BEHAVIOR

### 5.1 — Desktop map chrome uses `dvh` for peek sheet heights (styles.css:1856-1864) but mobile uses `vh` in `mapPad()` (app.js:818)
**File:** `web/styles.css:1856-1864`, `web/app.js:818`
**Issue:** `.map-peek-sheet[data-detent="..."]` uses `22dvh`, `50dvh`, `92dvh` (styles.css). But `mapPad()` in app.js uses `window.innerHeight` (`vh`). On mobile browsers with dynamic toolbars, `vh` and `dvh` diverge. The peek sheet sizes correctly with `dvh`, but the map padding (which positions the sheet relative to the map) uses `vh` — mismatch on Safari mobile.
**Fix:** Use `window.visualViewport?.height ?? window.innerHeight` in `mapPad()` for mobile, or accept the discrepancy and test on iOS Safari.

### 5.2 — `bottom-nav` width: `min(288px, calc(100vw - 28px))` (styles.css:652) — on mobile <320px, `100vw - 28px` could be <260px, shrinking the nav. Acceptable. ✅

On a 390px phone these fit, but on a 320px device (`--frame-mobile-w: 390px` is the design target, not the min).
**File:** `web/components.css:578, 647, 699, 760`
**Issue:** Several component widths are hardcoded to 358px or 370px. The design target is `--frame-mobile-w: 390px`. If the app is ever used on a 320px device, these components overflow.
**Fix:** Change hardcoded pixel widths in components.css to `min(358px, 100vw)` or `width: 100%; max-width: 358px` for production use. The preview specimen can keep fixed widths.

### 5.4 — `renderMemoriesScreen` map mode: height fixed at `480px` (app.js:2821)
**File:** `web/app.js:2821`
**Issue:** The embedded memories map has `height:480px` hardcoded. On a 600px-tall phone, that's 80% of the screen. No responsive adjustment.
**Fix:** Use `height: min(480px, calc(100vh - 180px))` or similar, or `height: 40vh`.

### 5.5 — Breakpoint comments say "mobile <768, tablet 768-1023, desktop >=1024, wide >=1180" (app.js:799-800) but the actual `mapPad()` only distinguishes desktop/tablet/mobile (3 tiers). No "wide" tier handling.

## 6. JAVASCRIPT ARCHITECTURE

### 6.1 — `render()` does full innerHTML replacement on every state change (app.js:4440)
**File:** `web/app.js:4440`
**Issue:** The main `render()` function sets `app.innerHTML = ...` which destroys all event listeners and re-creates the entire DOM tree on every render. Event handlers are re-bound in `bindHandlers()` (app.js:3998). This is a common pattern for small apps but causes:
- Loss of focus (e.g., typing in chat input triggers re-render → focus lost)
- No smooth transitions between states
- Memory churn from GC of old DOM

The chat screen is especially affected: typing in the composer doesn't trigger render (good — `oninput` only updates `state.chatQuery` but doesn't render). But sending a message calls `render()` which destroys the input and refocuses — acceptable.

**Fix (non-blocking):** For the chat input, save and restore `document.activeElement` + selection range across renders. Currently `chat-input` `oninput` only updates state and calls `render()` (app.js:4072-4079) — but `render()` replaces the input, so the cursor jumps to the end. The code does try to restore selection (lines 4076-4079) but the input element is a *new* DOM node after innerHTML replacement, so `nextCsi.focus()` works but the cursor position is restored. This is actually handled. ✅ But the pattern is fragile.

### 6.2 — `state` object is a single monolithic object (app.js:572-625) with 50+ properties.
**Issue:** No separation between UI state (tab, sheetDetent, sheetTab) and data state (me, partner, messages). No reactivity — manual `render()` calls everywhere.

**Fix (non-blocking):** Acceptable for the app's scale. Consider splitting if the app grows.

### 6.3 — `apiFetch` retry logic: on 401, attempts token refresh and retries once (app.js:954-956). ✅ Good.

### 6.4 — WebSocket reconnect: on close, retries after 3500ms (app.js:1334). ✅ But no exponential backoff — if the server is down, it retries every 3.5s forever.
**File:** `web/app.js:1332-1336`
**Issue:** `ws.onclose` always schedules a reconnect in 3500ms regardless of how many times it has reconnected. No backoff, no max retry cap.
**Fix:** Add a `wsReconnectAttempts` counter and exponential backoff (e.g., 3.5s, 7s, 14s, cap at 30s). Reset on successful connect.

### 6.5 — `syncAllData` uses `Promise.all` with `.catch(() => ({...}))` per endpoint (app.js:1213-1219). ✅ Graceful degradation. But if one endpoint throws a non-401 error, the error is swallowed and the remaining data renders with empty arrays. Acceptable. ✅

### 6.6 — `completePairAuthSuccess` calls `connectWebSocket()` before `syncAllData()` in the invite-code pathway (app.js:1531-1537).
**File:** `web/app.js:1531-1537`
**Issue:**
```js
if (state.partner || !state.inviteCode) {
  await syncAllData();
  connectWebSocket();
  startBrowserLocationWatch();
} else {
  connectWebSocket();
}
```
When joining with an invite code (`state.partner` is null and `state.inviteCode` is set), it connects the WebSocket *before* syncing data. The WS will receive events before the local state is populated. Acceptable (WS events update state incrementally), but the initial `syncAllData` should come first to have baseline state.
**Fix:** Swap the order: `syncAllData()` first, then `connectWebSocket()`.

### 6.7 — `handleGoogleCodeCallback` is called in `boot()` before `loadServerConfig()` only when `!native` (app.js:4492-4501). On native, `loadServerConfig()` runs first (line 4503) and then the access token check. But on web, the Google callback is handled *before* the server config is loaded — meaning if the server config changes between the callback and the config load, there's a race. Acceptable because the callback only processes the code → tokens, and the config is for future logins. ✅

### 6.8 — `proceedToSpaceSetupStep` is called from `window.onOursGoogleAuthFallback` (app.js:1786) when the server has no Google client ID. This moves the user to step 2 of onboarding. But if the user was already on step 2, it re-renders without changing state. Acceptable. ✅

### 6.9 — `bindHandlers` is called from `render()` (app.js:4460) and also from `bindNavAndRailHandlers()` which is called from `bindHandlers()` (app.js:3999) and also from the map overlay update path (app.js:4402, 4411). Potential double-binding:
**File:** `web/app.js:4399-4404`
**Issue:** In the map-tab update path (lines 4384-4415), `bindNavAndRailHandlers()` is called after replacing the rail (line 4402). Then `bindMapOverlayHandlers()` is called (line 4411). But `render()` is NOT called in this path — instead the overlay is updated in place. This is correct (avoids full re-render). However, `bindNavAndRailHandlers()` re-binds all `[data-tab]` and `[data-rail-bell]` handlers on every map overlay update — which happens frequently (on every WS location message). This adds overhead but not a bug. ✅ Low severity.

### 6.10 — `renderDesktopRail` computes `nextRailHtml` and compares with `existingRail.__lastHtml` (app.js:4395-4403). This is a dirty-check to avoid unnecessary DOM replacement. ✅ Good pattern. But `__lastHtml` is set on the *new* node (line 4400), not the existing one — if the replace doesn't happen (HTML identical), the existing node's `__lastHtml` is stale. Actually the code replaces only if different (line 4395), so this is fine. ✅

### 9.1 — All user-controlled data in template literals is passed through `escapeHtml()` (app.js:689-696). ✅ Verified: `state.spaceName`, `state.me?.name`, `state.partner?.name`, `state.me?.email`, `gMail`, `gName`, `pName`, `mName`, `inviteCode`, `place names`, `notes`, `messages`, `serverUrl`, `serverStatusText` — all escaped.

The data in the pin HTML (`initial`, `pillText`, `subText`, `batPct`) all come from `state.me?.name`, `state.partner?.name`, `t()` translations, and `loc?.battery_pct`. `initial` is derived from `name?.slice(0,1).toUpperCase()` — a single character, safe. `pillText` comes from `t()` or `"mePin"/"livePin"` — safe. `batPct` is a number. ✅

### 9.11 — **No CSP meta tag or header in the HTML files:** `assets-preview.html` and `tokens-preview.html` have no `<meta http-equiv="Content-Security-Policy">`. ## 10. PERFORMANCE (BUNDLE SIZE, REFLOWS)

### 10.1 — **Bundle size:** `app.js` is 4513 lines, ~160KB minified (estimated). No code splitting. The entire app loads as one IIFE. For a PWA this is acceptable but could be split: onboarding code (~600 lines) could be lazy-loaded after auth.

### 10.2 — **`render()` full innerHTML replacement causes layout thrash:** Every render replaces `app.innerHTML` (app.js:4440), which forces a full layout calculation. On a map tab update (e.g., WS location message), the code updates only the overlay (lines 4406-4413) — good, avoids full re-render. But on tab switches (e.g., map → chat), full innerHTML replacement happens. Each tab switch tears down the map instance (app.js:4418-4428) and rebuilds it. The map destruction + recreation on every tab switch is expensive.
**File:** `web/app.js:4418-4428`
**Issue:** When leaving the map tab, `mapInstance.remove()` is called and `mapInstance = null`. When returning to the map tab, `initOrUpdateMap()` creates a new `maplibregl.Map`. This means the map re-loads its style (vector tiles) on every tab switch.
**Fix:** Keep `mapInstance` alive across tab switches. Only destroy it on auth state change or server URL change. The map's `style` is already built by `buildMapStyle()` which is cheap (in-memory GeoJSON). The vector tile source is cached by MapLibre. Keeping the instance alive would avoid tile re-requests.

### 10.3 — **`initOrUpdateMap` checks `mapInstance.getContainer() === container`** (app.js:2546) — if the container is the same and the theme hasn't changed, it skips rebuild. ✅ Good. But this only triggers when `render()` is called AND the map tab is active. On a tab switch away and back, the container is destroyed and recreated (because `render()` replaces `app.innerHTML`), so `mapInstance` is null and a full rebuild happens. See 10.2.

### 10.4 — **`hydratePhotos()` is called multiple times:** In `updateCheckInPins()` (app.js:2692), in `bindHandlers()` (app.js:4247), in the map overlay update path (app.js:4412), in `openLightbox()` (app.js:3751), in `renderMemoriesScreen` map mode (app.js:4056). Each call queries `document.querySelectorAll("img[data-photo-id]")` and loops. Multiple calls on the same render cycle are redundant.
**File:** `web/app.js:2692, 4247, 4412, 3751, 4056`
**Issue:** `hydratePhotos()` is called 5 times in a single render cycle in some paths.
**Fix:** Call `hydratePhotos()` once per render, at the end of `bindHandlers()` (already done at line 4247). Remove the other calls, or guard with a flag.

### 10.5 — **`Promise.all` in `syncAllData`:** 6 parallel fetches (app.js:1213-1219). Each fetches a different endpoint. On a slow connection, all 6 run concurrently — good for latency but can saturate the connection. Acceptable. ✅

### 10.6 — **`buildMapStyle()` creates 25+ GeoJSON features with street grids:** Lines 2476-2489 create 24 street features (12 horizontal + 12 vertical) with hardcoded coordinates relative to `centerLonLat`. This is called every time the map is created or the theme changes. The GeoJSON is small (in-memory). ✅ But: if the theme changes frequently (e.g., auto theme toggling with system preference), the map is rebuilt with a new style each time. The `resolveMapThemeKey()` check in `initOrUpdateMap` (app.js:2546) prevents this unless the theme key actually changes. ✅

### 10.7 — **`makeCircleRing` computes 48-point circle for each place:** Used in `updatePlacesLayer` (app.js:2629). For N places, computes 48*N points. N is typically <10. ✅

### 10.8 — **`renderMapOverlayHtml()` builds a large HTML string:** Lines 2051-2341 build the entire overlay HTML as a string. On every WS location message, this string is rebuilt (via `render()` → map tab path lines 4406-4409). The dirty check (`existingOverlay.__lastHtml !== nextOverlayHtml`) prevents DOM replacement if the HTML hasn't changed. ✅ But the string is still built every time. For a location update that doesn't change the overlay content, the string building is wasted.
**Fix:** Only rebuild the overlay HTML when relevant state changes (partner location, sharing paused, sheet detent, etc.), not on every WS message. Currently `render()` is called on every WS message (app.js:1292, 1299, 1307, 1318, 1325) — this triggers the overlay HTML rebuild even if nothing changed.

### 10.9 — **`connectWebSocket()` is called from `completePairAuthSuccess` (app.js:1533, 1536) and from `boot()` (app.js:4497). If `completePairAuthSuccess` is called and the user already has a WS connection (e.g., re-auth), the old socket is closed and a new one opened. ✅ Acceptable. But: `resetClientSession` closes the waiting socket (app.js:641-643). ✅

### 10.10 — **`addEventListener("keydown", ...)` in `boot()` adds a global Escape → closeModal listener (app.js:4474). This is added once on boot. ✅ But: if `boot()` is called again (it's not — it's called once at the bottom of the IIFE), the listener would duplicate. ✅
